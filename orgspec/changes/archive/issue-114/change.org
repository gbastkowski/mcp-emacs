* Intent
`orgspec_parse` renders a change by prefixing the requirements with the
change *id* and a machine-facing `(from <tracker>:<issue>)` preamble
(e.g. `issue-63 (from github:gbastkowski/mcp-emacs#63)`). On PR #110
Gunnar called the id prefix machinery leaking into a human-facing line:
the traceability data already lives where it belongs (the buffer-level
TRACKER/ISSUE properties on the change file), so the render should lead
with the change's **human title** (its `#+TITLE:`) and, only when a
back-link exists, add a quiet second line such as `↳ github#63`.

The agreed rework (PR #110 comment 4035191962, `yes`) did not ship with
the merge (ead1a338) and is tracked here so it is not dropped. This is a
render-only change to `orgspec-mcp--format-change`; nothing about where
the traceability data is stored changes.

* Scope
In scope:
- `orgspec_parse` (via `orgspec-mcp--format-change`) leads the rendered
  change with the change's human title (its `#+TITLE:`), falling back to
  the change id when no title is set.
- When the change carries a back-link (a TRACKER or ISSUE buffer
  property), a quiet second line renders it as `↳ <tracker>#<issue>`,
  with the issue tail taken from the last `#` reference in the ISSUE
  property.
- The change model gains a `title` slot, parsed from the buffer-level
  `#+TITLE:` keyword alongside the existing TRACKER/ISSUE properties.
- `test/orgspec-mcp-test.el` updated to the new render.

Out of scope:
- No change to where TRACKER/ISSUE live (buffer properties stay); no
  change to the stored change data, the archive, or the fold.
- `orgspec-status` output is untouched.

* Approach
- 1. Parse the title with the data it belongs with:
  `orgspec-parse-change` already reads the buffer-level TRACKER/ISSUE
  properties; add the `#+TITLE:` keyword (a small buffer-keyword reader
  next to `orgspec-parse--buffer-property`) and carry it on the change as
  a new `title` slot, so title and back-link travel together.
- 2. Render title not id, back-link quiet: `orgspec-mcp--format-change`
  leads with `orgspec-change-title` (falling back to `orgspec-change-id`)
  and, when either TRACKER or ISSUE is present, adds a `↳ <tracker>#<…>`
  line under it.  The ISSUE property may carry a full `owner/repo#N`
  reference, so the quiet line takes the trailing `#N` tail and joins it
  to the tracker (bare `↳ tracker#63`), keeping the example shape Gunnar
  approved rather than repeating the repo in the render.

`orgspec_parse` SHALL render a change leading with its human title (the

- THEN the rendered change leads with the change id
