#+TITLE: issue-125

* Intent
~mcp-emacs-apply-diff-inline-limit~ is an integer cutoff: a unified diff at or
below it renders inline in the conversation buffer, a larger one opens
~mcp-emacs--ediff-review~.  Setting it to ~0~ forces ediff for everything;
there is no way to express the opposite — "always review inline, whatever the
size".  Opening ediff is a much heavier interruption than the per-diff value
justifies when the human is mid-task: with the default
~mcp-emacs-ediff-window-direction~ of ~plain~ it takes over the whole frame,
and the layout churn costs more attention than reading the diff does.  The
inline surface already supplies accept, reject, and ~C-c C-e~ to escape into a
full ediff for the diff that actually wants one, so dropping
ediff-by-default loses nothing — the human opts in per diff instead of opting
out per diff.

The fix: treat a negative ~mcp-emacs-apply-diff-inline-limit~ (concretely ~-1~)
as "never open ediff by default", so every review renders inline regardless of
size.  Two invariants must survive: the forced-ediff *fallbacks* are not a
"default" — when no conversation buffer can be resolved, or the conversation
cannot take the review (~condition-case~), ediff is still the surface, so
~-1~ means "no ediff by default", not "no ediff ever"; and a very large diff
pasted inline is its own kind of unusable, so the inline view SHALL keep a
large diff navigable (fold/scroll) rather than dumping an unreadable wall into
the conversation buffer.

* Scope
In scope:
- ~-1~ for ~mcp-emacs-apply-diff-inline-limit~ (any negative value) makes
  ~mcp-emacs--apply-diff-inline-p~ return non-nil for any diff that could be
  produced; a diff that could not be produced (nil text) still goes to ediff.
- ~0~ and positive values keep their current meaning unchanged.
- The two ediff fallbacks stay live under ~-1~: an unresolvable conversation
  buffer and the ~condition-case~ for a conversation that cannot take the
  review both still open ediff.
- ~C-c C-e~ keeps escaping an inline review into a full ediff under ~-1~.
- A large inline diff renders folded/navigable: its hunk headers are
  outline headings so the human can collapse it, and hold state is
  cleaned/reverted when the review resolves (accept / reject / jump / timeout).

Out of scope:
- The IDE ~open_diff~ path in ~elisp/mcp-emacs-ide.el~, which goes straight to
  ~mcp-emacs--ediff-review~ and never consults the inline gate — the issue
  flags it as possibly its own issue.
- Changing the default value (~40~) or the meaning of ~0~ / positive limits.
- Changing the ediff window-layout behaviour (~mcp-emacs-ediff-window-direction~).

* Approach
- ~elisp/mcp-emacs.el, mcp-emacs--apply-diff-inline-p~: return non-nil for
  any non-nil DIFF-TEXT when the limit is negative:
  ~(and diff-text (or (< mcp-emacs-apply-diff-inline-limit 0)
  (<= (length (split-string diff-text "\\n" t)) limit)))~.  Nil DIFF-TEXT still
  short-circuits to nil.
- Update the ~mcp-emacs-apply-diff-inline-limit~ defcustom docstring to say a
  negative value means every producible diff renders inline (ediff stays the
  forced fallback and reachable via ~C-c C-e~); extend ~:type~ to admit
  negative integers.
- ~mcp-emacs--inline-review~: when the rendered diff is larger than a fold
  threshold, enable folding in the conversation buffer so each diff hunk
  header (~^@@ ~) is a collapsible outline heading.  Preserve and restore the
  conversation buffer's prior outline state (minor-mode + regexp) around the
  review so tearing the surface down leaves the buffer as it was.  The existing
  teardown path (accept / reject / jump / timeout) runs the restore.
- Tests in ~test/mcp-emacs-apply-diff-test.el~: ~-1~ inlines a diff above any
  positive limit; ~-1~ still treats nil DIFF-TEXT as too large (dispatch → ediff);
  ~-1~ with no conversation buffer still opens ediff (fallback preserved); a
  large inline diff gets collapsible outline headings that revert on resolve.
- Verify with the repository's own entry point on a separate Emacs:
  ~bin/test-emacs.sh --compile --strict~ and the full suite in the work tree
  on akiko (Emacs 31.1), plus CI as the authoritative cross-check.
