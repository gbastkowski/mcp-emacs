#+TITLE: show-a-what-s-new-screen-after-an-upgrade
#+PROPERTY: TRACKER github
#+PROPERTY: ISSUE gbastkowski/mcp-emacs#98

* Intent
A user upgrading mcp-emacs should be able to find out what changed without
reading the git log. Today the release notes exist only as the GitHub
release body (merged PR titles since the previous tag, generated by
`release.yml`), which requires visiting the web. Gunnar's answer scoped the
feature: keep a local `.mcp-emacs-last-seen` stamp file for the previously
installed version, ship a release-notes Org file with each release, and let
a What's-new command display those notes as an Org buffer — one top-level
headline per release — so each upgrade shows the notes for the releases
installed since the stamp. The project does not depend on Doom, so how to
surface the command in Doom's home screen is *documented*, not wired up.

This matches the issue's decision thread and does not invent new surface:
the notes come from the same merged-PR source of truth `release.yml`
already uses, and the command is an ordinary interactive entry point a user
binds or calls at will.

* Scope
In scope:
- A release-notes Org file written by `release.yml` on every release, one
  per release tag, containing one top-level headline per release with the
  merged-PR lines that today go into the GitHub release body.
- A local stamp file `.mcp-emacs-last-seen` holding the last version whose
  notes were shown (the "previously installed version" per the issue).
- An interactive command that shows the release notes for every release
  newer than the stamp in an Org buffer (read-only), each release its own
  top-level headline, and then bumps the stamp to the installed version.
- Documentation of how to surface that command in Doom's home screen, since
  mcp-emacs itself does not depend on Doom.

Out of scope:
- Any Doom dependency or a built-in Doom home-screen integration.
- A hand-maintained CHANGELOG (the merged-PR source of truth stays).
- Pinging the network to decide a version is newer: the stamp answers
  "previously installed version" offline.
- Auto-popup on load without the user asking; the command is the entry
  point (an optional future slice can add a load-time hook).

* Approach
- Extend `release.yml` to also write a release-notes Org file into the repo
  at release time (e.g. `news/release-<ver>.org`), carrying the same
  merged-PR lines as the GitHub body but under a top-level headline
  `* Release vX.Y.Z`. Commit it so it ships with the checkout — the What's
  new screen then reads it from the installed files, no network.
- Add `elisp/mcp-emacs-whats-new.el`: `mcp-emacs-whats-new` finds the
  release-notes Org files installed alongside the elisp, filters to those
  whose version is newer than the version stamped in `.mcp-emacs-last-seen`
  (defaulting to the lowest known release when the stamp is missing), opens
  them in a read-only Org buffer with one headline per release, and writes
  the installed version (the elisp header `Version:` of `mcp-emacs.el`) back
  to the stamp.
- Where to look for the notes: relative to `mcp-emacs.el`'s install
  directory (`news/` next to it), falling back to `user-emacs-directory`
  based locations so both a checkout and a manual copy work.
- Document the Doom binding in `README.md` (a short "Doom" note showing how
  to add `mcp-emacs-whats-new` to the Doom home screen); no code wiring.

* Tasks
- [ ] `release.yml` writes `news/release-<ver>.org` (top-level headline + merged-PR lines) and commits it
- [ ] `elisp/mcp-emacs-whats-new.el`: resolve installed version from the `mcp-emacs.el` header
- [ ] locate `news/*.org` next to the elisp (checkout + manual-copy fallbacks)
- [ ] read `.mcp-emacs-last-seen`; select notes newer than the stamp; default to all when stamp absent
- [ ] show them in a read-only Org buffer, one headline per release
- [ ] bump the stamp to the installed version
- [ ] tests in `test/mcp-emacs-whats-new-test.el` (selection, stamp bump, buffer rendering)
- [ ] README note on adding it to Doom's home screen

Emacs SHALL provide an interactive command `mcp-emacs-whats-new` that opens a
read-only Org buffer containing the release-notes Org files shipped with the
installed mcp-emacs — one top-level headline per release — for every release
newer than the previously-installed version recorded in a local
`.mcp-emacs-last-seen` stamp file.  The command SHALL write the installed
version (from the `Version:` header of `mcp-emacs.el`) back to that stamp
after showing the notes, so each upgrade shows the notes for the releases
installed since the stamp and nothing is shown twice.  When the stamp is
absent, SHOW all shipped release notes rather than none.  The installed
version MUST come from the local checkout, never from the network.
*** One-time notes on upgrade
- GIVEN an installed version newer than the `.mcp-emacs-last-seen` stamp and release-notes Org files for the intervening releases
- WHEN `mcp-emacs-whats-new` is invoked
- THEN a read-only Org buffer shows one top-level headline per intervening release with the notes, and the stamp is updated to the installed version
*** Nothing new after the stamp is current
- GIVEN an installed version equal to the `.mcp-emacs-last-seen` stamp
- WHEN `mcp-emacs-whats-new` is invoked
- THEN no notes are shown and the installed version is re-stamped
*** First run shows everything when no stamp exists
- GIVEN no `.mcp-emacs-last-seen` stamp file
- WHEN `mcp-emacs-whats-new` is invoked
- THEN all shipped release-notes Org files are shown and a stamp is created at the installed version
