* An interactive diff/apply tool presents a proposal via ediff
The system SHALL expose an MCP tool that accepts a file path and proposed new
content, opens an ediff session comparing the file's current content against
the proposal, and lets the human review, edit, accept, or reject it
interactively before the tool returns.
The outcome SHALL be determined by an explicit human accept or reject action
during the session, not by whether the buffer content changed; accepting SHALL
apply the proposal (or the human's edited version of it) to the file and SHALL
write it to disk, so a returned status of ~applied~ means the file on disk
holds that content; rejecting SHALL leave the file unchanged, and quitting
without an explicit accept SHALL be treated as a rejection.
** An accepted proposal is applied
- GIVEN a diff call with a path and new content
- WHEN the human accepts the proposal without editing it
- THEN the proposed content is written to the file on disk and a status of
  ~applied~ is returned with the final content
** A rejected proposal changes nothing
- GIVEN a diff review in progress
- WHEN the human rejects the proposal
- THEN the file's buffer is left unchanged and a status of ~rejected~ is
  returned
** A human edit wins over the proposal
- GIVEN a diff review in progress
- WHEN the human edits the proposed content and then accepts
- THEN the file on disk holds the human-edited content, not the original
  proposal, and a status of ~applied~ is returned
** Quitting without accepting is a rejection
- GIVEN a diff review in progress
- WHEN the human quits the ediff session without explicitly accepting
- THEN the file's buffer is left unchanged and a status of ~rejected~ is
  returned
* Diff/apply waiting does not block the Emacs event loop
While waiting for the human's decision, the diff tool SHALL yield to the Emacs
event loop so that human edits, timers, and other MCP tool calls continue to
be processed.
** Other work proceeds during a diff wait
- GIVEN the diff tool is waiting for the human to resolve the ediff session
- WHEN other MCP tool calls arrive or buffers are edited
- THEN they continue to be handled

* The diff/apply wait is bounded by a timeout
The diff tool SHALL apply a default timeout when none is given and MUST cap
the timeout at a defined maximum, so the call cannot hang indefinitely. When
the timeout elapses the tool SHALL report a status of ~timeout~ -- distinct
from ~rejected~ -- and MUST leave the file on disk unchanged.
** An unanswered review times out
- WHEN the timeout elapses for a review the human neither accepts nor rejects
- THEN the ediff session is abandoned, the file on disk is left unchanged,
  and a status of ~timeout~ is returned
** An excessive timeout is capped
- GIVEN a requested timeout above the maximum
- WHEN the diff tool runs
- THEN it waits no longer than the maximum
** A timeout is not reported as a rejection
- GIVEN a review the human did not answer and a timeout that elapses
- WHEN the ediff session is force-quit to end the wait
- THEN the reported status is ~timeout~, not ~rejected~

* The filing chain is resilient
The system SHALL attempt to create the issue through more than one mechanism
so that filing succeeds whenever any one of them is available, trying in
order: the GitHub MCP tool if available, then the ~gh~ CLI, then a direct ~gh
api~ call.
If none is available, the system SHALL report that it could not file the issue
and SHALL surface the issue title and body so the user can file it manually.
** The preferred mechanism wins
- GIVEN the GitHub MCP tool is available
- WHEN the tool files an issue
- THEN it is created through the MCP tool and the lower-priority mechanisms
  are not attempted
** The CLI is the fallback
- GIVEN the GitHub MCP tool is unavailable but the ~gh~ CLI is
- WHEN the tool files an issue
- THEN it is created through the ~gh~ CLI
** No mechanism surfaces the draft
- GIVEN none of the filing mechanisms is available
- WHEN the tool runs
- THEN no issue is created, the failure is reported, and the composed title
  and body are returned for manual filing

* Reports target mcp-emacs, not arbitrary repositories
The tool SHALL be scoped to filing issues about mcp-emacs itself and SHALL
target the mcp-emacs repository; it is not a general-purpose issue creator for
arbitrary repositories.
** The target repository is fixed
- GIVEN any call to the tool
- WHEN it creates an issue
- THEN the issue is created on the mcp-emacs repository and the caller does
  not choose an arbitrary target repository

* Non-HTTP dispatch honours async tools

The server SHALL route a tools/call that names a tool declaring
`:async-handler` through that handler on every dispatch path, including
the non-HTTP direct dispatch and `orgspec-mcp-call`; the result SHALL be
delivered via the caller-supplied completion callback.

** WHEN a tool declares an :async-handler and is called outside HTTP
    THEN the tool is dispatched through :async-handler
    AND the caller receives the completion via its callback
    AND the dispatch returns a deferred marker instead of a blocking result

** WHEN a tool declares no :async-handler
    THEN the existing synchronous dispatch is unchanged
    AND the text result is returned as before

** WHEN a caller cannot defer and the tool declares :async-handler
    THEN the dispatch refuses loudly with an error
    AND no blocking wait is started

* A session file change wait is served without blocking the process filter
The ~org_task_wait_for_change~ tool SHALL be registered with an
~:async-handler~ alongside its synchronous ~:handler~, shaped like
~apply_diff~'s: over HTTP the wait SHALL start and return to the Emacs event
loop immediately rather than occupy the process filter, and the deferred
request SHALL be answered from a timer callback.
** Returns without occupying the filter over HTTP
- WHEN ~org_task_wait_for_change~ is called over HTTP for a session file that has not changed past its baseline
- THEN the handler returns to the event loop immediately and the response is written later, once the change is observed or the timeout elapses
** Single delivery when the change is observed
- GIVEN an async wait in progress with a baseline token
- WHEN the session buffer is edited past that token before the timeout
- THEN the deferred response carries the change flag and current session view exactly once
** Single delivery when the timeout elapses
- GIVEN an async wait in progress with a baseline token
- WHEN no edit occurs before the bounded timeout
- THEN the deferred response carries the no-change flag and current session view exactly once
** The synchronous fallback stays
- THEN ~org_task_wait_for_change~ SHALL keep its ~:handler~ so callers that dispatch directly (outside HTTP) are served synchronously, exactly as ~apply_diff~ does
* Report buffer opens in org-mode
The interactive bug-report and feature-request commands SHALL open their

** Buffer starts in org-mode

  composition buffer
- THEN the buffer's major mode is ~org-mode~
- AND the prompt send/abort bindings still work on top of it

- AND the title is the first line, unchanged
** No markup backend available

** Org headline left empty

- THEN it is removed from the filed body
* Small diff reviews render inline in the conversation buffer
The ~apply_diff~ review SHALL render a small diff inline in the conversation

and SHALL open ediff for a diff larger than the inline limit. A diff is small

= mcp-emacs-apply-diff-inline-limit =. Ediff SHALL remain reachable from the

** A small diff appears inline
- GIVEN an ~apply_diff~ whose diff fits the inline limit
- WHEN the review starts
- THEN it renders as text in the conversation buffer rather than opening ediff
** A large diff stays in ediff
- GIVEN an ~apply_diff~ whose diff exceeds the inline limit
- WHEN the review starts
- THEN it opens ediff as before
** Ediff is reachable from the inline view

- WHEN the human presses the jump key
- THEN a real ediff session against the same buffers opens
* Inline accept and reject record the same outcome
Accepting an inline review SHALL apply the proposal to the file and report
the same outcome format the ediff accept returns (~~Status: applied~~ plus
the final content); rejecting SHALL leave the file unchanged and report
~~Status: rejected~~. A hand-edit made to the file's buffer before accepting
SHALL be kept, exactly as with the ediff accept path. Whichever surface the
human resolves first — inline or the jumped-to ediff — SHALL be the only
outcome delivered.
** Inline accept applies the change
- GIVEN an inline diff review whose proposal is untouched beyond the diff
- WHEN the human accepts it
- THEN the proposal replaces the file content and the outcome reads
  ~~Status: applied~~
** Inline reject leaves the file alone
- GIVEN an inline diff review
- WHEN the human rejects it
- THEN the file is unchanged and the outcome reads ~~Status: rejected~~
** A hand edit survives an inline accept
- GIVEN the file's buffer was edited away from the original before accept
- WHEN the human accepts the inline review
- THEN the file keeps the hand-edit, matching the ediff accept rule
** One surface answers once
- GIVEN an inline review that the human jump-starts into ediff
- WHEN the human resolves it in ediff
- THEN the inline view does not deliver a second, competing outcome
