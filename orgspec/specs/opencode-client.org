* opencode-client implements agent-backend and publishes shared events

The OpenCode V2 client MUST define an agent-backend subclass, MUST
translate its SSE stream events into the shared :kind vocabulary and
publish them on agent-backend-event-functions, MUST derive its major
mode from agent-backend-mode, and MUST keep its public
opencode-client-* commands as thin wrappers over the generic methods.

** SSE text maps to :text
GIVEN opencode streams an assistant text part
WHEN the frame is applied
THEN a :text event is published on the shared hook

** Public commands stay stable
GIVEN the refactored client
WHEN opencode-client-send-prompt is called
THEN it dispatches through agent-backend-send and behaves as before

* opencode mid-turn input and replies use the shared primitives

The opencode backend MUST implement agent-backend-add-note as a
steering prompt (delivery: steer; note-policy :steer), and MUST
implement reply-permission and reply-question against the opencode
HTTP endpoints, using ~once~/~always~/~reject~ permission decisions and
keyed form answers rather than the V1 question protocol.

** A note steers the turn
GIVEN a turn is active
WHEN agent-backend-add-note is called
THEN a steer prompt is delivered and a :note event is published

** Permission is answered
GIVEN opencode requests permission
WHEN agent-backend-reply-permission is called
THEN the permission reply endpoint is used

** Questions are answered
GIVEN opencode asks a question
WHEN agent-backend-reply-question is called
THEN the question reply endpoint is used

* opencode exposes sessions through the shared surface

The opencode backend MUST implement list-sessions from the V2 session
API, MUST reattach to existing IDs for resume, and MUST report the
session's explicit location directory as its project root.

** Sessions are listed
GIVEN opencode serve has sessions
WHEN agent-backend-list-sessions is called
THEN they are returned as (:id :label :time) plists

** Resume recovers an existing session
GIVEN a persisted V2 session
WHEN agent-backend-resume is called
THEN its location and history are restored without creating a new session

* The client connects to a running opencode server
The system SHALL connect to an ~opencode serve~ HTTP endpoint at a
configurable host and port, verify a 2.x version through ~/api/info~, and support an
optional server password for HTTP basic auth.
The password MAY be configured directly or resolved by running a configured
shell command and using its trimmed standard output, so it can come from a
secret store.
When starting a server on demand, the client SHALL, if a launchd label is
configured, start it by kickstarting that launchd agent (so the server is
owned by launchd and outlives Emacs); otherwise it MAY start the server as a
child process.
** A healthy server is ready for requests
- GIVEN a reachable opencode server
- WHEN the client connects
- THEN the health check succeeds and the client is ready to issue requests
** An unreachable server errors clearly
- GIVEN a host and port the client cannot reach
- WHEN the client connects
- THEN a clear connection error is reported rather than an opaque failure
** A direct password authenticates
- GIVEN a password configured directly
- WHEN the client issues a request
- THEN it authenticates with HTTP basic auth using that value
** A password command authenticates
- GIVEN no direct password but a configured password command
- WHEN the client issues a request
- THEN it runs the command and authenticates with its trimmed output
** No configured password sends no header
- GIVEN neither a direct password nor a password command
- WHEN the client issues a request
- THEN it sends no authorization header
** An on-demand start prefers launchd
- GIVEN a configured launchd label
- WHEN the user starts the server on demand
- THEN the client kickstarts that launchd agent rather than spawning a child
  process

* The client manages opencode sessions
The system SHALL list, create, select, and delete opencode sessions through
the V2 server API, and track the active session separately for each project.
Creation SHALL include ~location.directory~ and listing SHALL filter by
directory. Projects SHALL share one configured service endpoint. Sessions
with equal titles SHALL keep distinct buffers, identified by endpoint and ID.
** Sessions are listed with enough detail to choose
- GIVEN a server with sessions
- WHEN the user lists them
- THEN the server's sessions are returned with enough detail to choose one
** A created session becomes active
- GIVEN the user creates a new session
- WHEN it is created on the server
- THEN it becomes the active session
** A deleted session is cleared
- GIVEN the user deletes a session
- WHEN it is removed on the server
- THEN if it was active the active session is cleared

* The client sends prompts and can interrupt
The system SHALL send a user prompt to the active session with a selectable
delivery mode (steer or queue) and SHALL be able to interrupt a running
session.
** A prompt starts streaming
- GIVEN an active session
- WHEN the user submits a prompt
- THEN the client posts it to the server and the response begins streaming
  into the chat buffer
** Steer delivery does not queue
- GIVEN a turn is in progress
- WHEN the user submits a prompt with steer delivery
- THEN the client delivers it as a steering message rather than queuing it
** An interrupt stops the turn
- GIVEN an active session running a turn
- WHEN the user interrupts it
- THEN the client asks the server to stop the running turn

* The conversation renders incrementally from the event stream
The system SHALL subscribe to the shared ~/api/event~ stream, filter all
business events by session ID before changing UI or requesting approval, and
render text/reasoning/tool lifecycle events incrementally. Event IDs SHALL
suppress duplicates without treating transient deltas as durable sequences.
** Assistant text streams in
- GIVEN the server emits message-part update events for assistant text
- WHEN they arrive
- THEN the chat buffer updates incrementally as the parts arrive, without
  waiting for the full turn
** Tool and reasoning activity is visible
- GIVEN the server emits tool-input or reasoning lifecycle events
- WHEN they arrive
- THEN the client reflects that activity in the buffer so the user can see
  what the agent is doing
** A lost stream is reported, not hung
- GIVEN an active event stream
- WHEN it ends unexpectedly or the server disconnects
- THEN the client stops rendering cleanly and reports the disconnection rather
  than hanging

* The client surfaces and answers permission and question requests
The system SHALL detect V2 permission requests and forms for the
active session and let the user answer them from Emacs, sending the reply back
to the server. Permission menus SHALL never write Claude settings. Form
collection SHALL preserve field keys, option values, numbers, booleans and
multiselect arrays; all fields SHALL be submitted in one reply. Conditional
fields SHALL depend on previously collected answers. External URL forms MAY
require the OpenCode web or terminal interface, but SHALL NOT be auto-answered.
** A permission request is answered
- GIVEN the server requests permission during a turn, for example to run a
  tool
- WHEN the user decides
- THEN the client presents the request and sends the decision back to the
  server
** A question is answered
- GIVEN the server asks the user a question during a turn
- WHEN the user replies or rejects
- THEN the client presents the question and sends the reply back to the server

* The client adds no hard package dependency
The client SHALL use ~plz~ for HTTP and SSE only when it is available, loaded
as a soft/optional dependency, so installing mcp-emacs does not require ~plz~.
** With plz it is used for HTTP and SSE
- GIVEN an Emacs where ~plz~ is loaded
- WHEN the client issues requests
- THEN it uses ~plz~ for HTTP requests and the SSE stream
** Without plz loading still succeeds
- GIVEN an Emacs where ~plz~ is not loaded
- WHEN mcp-emacs is loaded
- THEN loading succeeds and the client reports that it needs ~plz~ only when a
  client command is invoked

* The client unwraps the server response envelope
The V2 server returns most responses wrapped in a ~data~ envelope and
paginated lists alongside ~cursor.next~/~cursor.previous~. The transport SHALL
retain the entire response. Payload consumers MAY unwrap ~data~, but session
and history listing SHALL follow ~cursor.next~ without silently dropping older
items. Cursor requests SHALL omit ~order~. Flat ~/api/info~ responses SHALL
pass through unchanged.
** A wrapped object is unwrapped
- GIVEN a wrapped object response such as a created session ~{"data": {"id":
  …}}~
- WHEN the client reads it
- THEN it uses the inner object, so fields like the session id are read
  correctly
** A wrapped list is unwrapped
- GIVEN a wrapped list response such as ~{"data": [ … ], "cursor": …}~
- WHEN the client reads it
- THEN it uses the inner list as the collection
** A flat response passes through
- GIVEN a flat object with no ~data~ key, such as the health check
  ~{"version": "2.2.5", ...}~
- WHEN the client reads it
- THEN it uses the response unchanged

* Session history loads when a session is opened
When the client opens a chat buffer for a session, it SHALL subscribe first
and recover chronological, paginated history after ~server.connected~. This
SHALL avoid the history-before-subscription gap. History items without IDs
SHALL use stable content ordinals in the render model.
** Reattaching shows the prior conversation
- GIVEN a session that already has messages on the server
- WHEN the client opens it
- THEN existing messages are recovered without duplicating text that raced
  the snapshot request
** A new session renders empty
- GIVEN a freshly created session with no messages
- WHEN the client opens it
- THEN the buffer renders empty and streaming proceeds normally
** History parts map to the render model
- GIVEN history containing a user message with text and an assistant message
  with text, reasoning, and tool content parts
- WHEN it is rendered
- THEN each part is rendered the same way the equivalent live streamed part
  would be

* opencode surfaces V2 forms through the shared menu
The system SHALL, when the client receives ~form.created~ for its session,
publish a ~question-request~ event and collect every field through the shared
answer menu. The keyed answer SHALL use the V2 form reply endpoint.
** A form.created event raises the menu
- WHEN the opencode SSE stream delivers ~form.created~ for this session
- THEN a ~question-request~ event is published and an answer menu is shown for
  the active session
** The reply reaches the endpoint
- WHEN an answer is chosen in the answer menu for an opencode question
- THEN the complete keyed answer is posted to the form reply endpoint
** A manually-asked question still works
- WHEN the human invokes the manual answer command with a pending request-id
- THEN the answer is delivered through the same reply path

* V2 reconnect restores state without replaying mutations
An unexpected EOF or error SHALL schedule one reconnect. The connection marker
SHALL trigger reconciliation of history, active execution, pending permissions
and pending forms. Prompts and approvals SHALL NOT be retried automatically.
Events racing recovery SHALL trigger a new snapshot rather than append duplicate
deltas. Requests answered elsewhere SHALL close locally without a second reply.
Explicit quit or buffer destruction SHALL cancel timers and close local menus,
but SHALL NOT delete the remote session or stop the shared service.
** A missed form is recovered
GIVEN a form was created while Emacs was disconnected
WHEN the client reconnects
THEN the pending form is shown from the session's form inventory
** Explicit quit stays disconnected
WHEN the user quits while reconnect is pending
THEN no timer reopens the stream

* V2 execution events drive turn state
The backend SHALL report working from ~session.execution.started~ and idle
from execution success, failure or interruption. An individual step ending
with ~tool-calls~ SHALL NOT complete the turn. Disconnected clients SHALL
report finished without claiming the remote execution was stopped.
** A tool-calls step is not a completed execution
GIVEN an execution is working
WHEN a model step ends to call tools
THEN the backend remains working

* Shared-service discovery preserves endpoint credentials
The client SHALL discover OpenCode's registered shared service before starting
a standalone fallback. Discovery SHALL respect ~XDG_STATE_HOME~, verify the V2
server, and carry its password through HTTP requests, conversation creation,
and SSE subscriptions. Separate project connections SHALL retain their own
location directories even when they share one service. Discovery MAY be disabled
to use only an explicitly configured endpoint.
** A discovered password is not replaced by another server's password
GIVEN a healthy service registration and a different global password
WHEN its session is opened and the client subscribes to events
THEN both control requests and streaming use the registered service credential

* Opening an OpenCode conversation offers immediate composition
The preferred OpenCode start command SHALL create a session and immediately
offer its prompt composition buffer. Rendering SHALL distinguish human prompts,
reasoning and tool statuses, with optional Markdown fontification of assistant
prose and a readable plain-text fallback.
** A fresh session is ready for input
WHEN the human starts OpenCode through the shared backend command
THEN the conversation and its prompt composer are shown together

* Tool calls expose expandable arguments and results
Tool blocks SHALL display the tool name, lifecycle status, arguments, bounded
result previews and structured errors. They SHALL identify file attachments
without inserting embedded binary data, and MAY show durations when observed
timestamps are available. TAB anywhere in the block SHALL expand or collapse
the complete stored details without remote requests or conversation mutations.
Collapsed previews SHALL be bounded by both lines and characters. Expansion and
the reader's place SHALL survive stream renders and history refreshes.
** Long output is inspectable without overwhelming the conversation
GIVEN a tool result longer than the configured preview limits
WHEN the conversation renders
THEN a bounded preview and a visible expansion hint appear
AND TAB reveals the complete stored result and can collapse it again
** A completed call retains its arguments
GIVEN the client observed a tool's arguments while it was running
WHEN its result event arrives
THEN the completed block still shows those arguments alongside the result

* Session help is available from the conversation
The conversation SHALL bind ? to a keybinding help view in plain Emacs and
Evil normal/motion states. Help SHALL describe prompt composition, tool expansion,
interrupt, resume and disconnect controls, including inherited backend keys.
It SHALL open in a separate ordinary window and be dismissible with ? or q
without closing the conversation, disconnecting its stream or changing remote
execution. Repeated toggling SHALL NOT accumulate windows.
** Help is reachable under Evil
GIVEN point is in an OpenCode conversation in Evil normal or motion state
WHEN the human presses ?
THEN the session keybindings are shown instead of starting backward search
** Closing help leaves the conversation open
GIVEN the session help is visible
WHEN the human presses q in its help window
THEN only the help window is closed and the conversation remains available
