* The agent-backend class defines the conversation lifecycle interface

The agent-backend module MUST define an EIEIO base class with
cl-defgeneric methods for connect, quit, send, input, interrupt,
add-note, note-policy, reply-permission, reply-question, list-sessions,
resume, seed-history, project-root, and render, and MUST provide no-op or
user-error default implementations for the optional capabilities
(permission/question replies, history seeding, resume, sessions) so a
backend that lacks them needs no stubs.  agent-backend-input MUST
default to send, so only a backend that has to queue mid-turn text
itself needs a method.

** A minimal backend compiles against the defaults
GIVEN a backend subclass implementing only connect, send, interrupt,
add-note, note-policy, and quit
WHEN the module is byte-compiled
THEN the subclass is valid without further stubs

** Resume is optional
GIVEN a backend without a session store
WHEN agent-backend-resume is called
THEN a user-error explains that the backend cannot resume

** Replies are optional
GIVEN a backend that never asks for permission
WHEN agent-backend-reply-permission is called
THEN the default implementation is a no-op

* A shared event hook carries the backend-agnostic vocabulary

The agent-backend module MUST publish every conversation event as a
plist with a :kind symbol on the abnormal hook
agent-backend-event-functions, run with (BUFFER EVENT), and the :kind
vocabulary MUST cover at least started, prompt, text, tool-use,
tool-result, finished, interrupted, note, notes-delivered,
note-dropped, resumed, permission-request, question-request, and
error. Subscribers MUST ignore unknown kinds.

** Text events reach subscribers
GIVEN a backend publishes an assistant text event
WHEN a subscriber is registered on agent-backend-event-functions
THEN it is called with (BUFFER (:kind text ...))

** Unknown kinds degrade to silence
GIVEN a subscriber that knows only :text
WHEN an event with an unknown :kind is published
THEN the subscriber runs without error

* A shared conversation mode holds the instance and common keys

agent-backend-mode MUST derive from special-mode, MUST hold the backend
instance in a buffer-local variable, and MUST bind the common actions
(input, interrupt, quit, resume) in a shared keymap that derived
backend modes extend.  There MUST NOT be a separate note key: the input
key takes what the human has to say whether or not a turn is running.

** The instance is visible to subscribers
GIVEN a buffer in a derived backend mode
WHEN a subscriber reads the buffer-local instance
THEN it is the backend object of that conversation

** The common keys are bound
GIVEN a derived backend mode
WHEN the shared keymap is inspected
THEN input, interrupt, quit, and resume are bound, and no note key is
bound

* Session overview buffer

Emacs SHALL provide a single overview buffer listing every live AI session
across all backends, showing for each its backend, project, session identity,
state, and time since last activity.

** Sessions from several backends are listed together
- *GIVEN* a =claude-client= conversation, an =opencode-client= session, and an eat
  runner session are live at the same time
- *WHEN* the overview is opened
- *THEN* all three appear as rows, each labelled with the backend it belongs to

** Several conversations in one project are distinguished
- *GIVEN* two =claude-client= conversations are live in the same project
- *WHEN* the overview is opened
- *THEN* both appear as separate rows, distinguishable by their session identity

** No live sessions
- *GIVEN* no AI session is live in any backend
- *WHEN* the overview is opened
- *THEN* the buffer reports that there are no live sessions rather than showing an empty table with no explanation

* Session state is classified

The overview SHALL show each session's current state at the precision its
backend allows: for =claude-client=, distinguishing a session whose model is
mid-turn from one that is idle and from one whose process has exited; for the
eat runner and =opencode-client=, liveness only. A state MUST NOT be reported
more precisely than the backend can observe.

=opencode-client= is liveness-only for the same reason the eat runner is: it
keeps no per-buffer turn state and never publishes a =finished= event, so a row
entering "working" could never leave it. Wiring opencode's discarded
=step-finish= signal (=opencode-client.el:500=) through as a =finished= event
would promote it to a working/idle backend, but that is a change to
=opencode-client.el= and is tracked separately; the overview gains the finer
state for free once it lands.

** Mid-turn session
- *GIVEN* a =claude-client= session whose model is working on a turn
- *WHEN* the overview renders that session's row
- *THEN* the row shows the working state

** Idle session
- *GIVEN* a =claude-client= session whose process is live and no turn is in progress
- *WHEN* the overview renders that session's row
- *THEN* the row shows the idle state

** Exited session
- *GIVEN* a =claude-client= session whose process has exited
- *WHEN* the overview renders that session's row
- *THEN* the row shows the finished state rather than reporting it as idle

** opencode session shows liveness only
- *GIVEN* a live =opencode-client= session buffer
- *WHEN* the overview renders its row
- *THEN* the row shows the live state and does not report a working or idle turn
  state, because opencode publishes no turn-end event

** Eat runner session shows process liveness
- *GIVEN* an eat runner session whose terminal process is live
- *WHEN* the overview renders its row
- *THEN* the row shows the live state

** Eat runner session with an exited process
- *GIVEN* an eat runner buffer whose terminal process has exited
- *WHEN* the overview renders its row
- *THEN* the row shows the dead state

** Eat runner state is not inferred beyond liveness
- *GIVEN* an eat runner session is live
- *WHEN* the overview renders its row
- *THEN* the row does not report a working or idle turn state, because the eat runner publishes no turn events

* Overview updates live

The overview SHALL update itself in response to session lifecycle events for
backends that publish on =agent-backend-event-functions=, without the human
refreshing it, and a failure while rendering MUST NOT affect the session that
triggered it.

** Turn start moves the row
- *GIVEN* the overview is displayed and a session is idle
- *WHEN* that session begins a turn
- *THEN* its row changes to the working state without a manual refresh

** Turn end moves the row
- *GIVEN* the overview is displayed and a session is mid-turn
- WHEN that turn finishes or is interrupted
- *THEN* its row leaves the working state without a manual refresh

** A render failure does not break the session
- *GIVEN* the overview is subscribed to the event hook
- *WHEN* rendering a row signals an error
- *THEN* the session that published the event continues unaffected

** Manual refresh still works
- *GIVEN* the overview is displayed
- *WHEN* the human requests a refresh
- *THEN* the buffer re-enumerates sessions and re-renders

* Sessions are actionable from the overview

The overview SHALL let the human act on the session under point — visiting it,
quitting it, and interrupting its current turn — without leaving the buffer.
Actions MUST take effect immediately: quitting a session SHALL NOT ask for
confirmation, even when that session is mid-turn.

** Visit a session
- *GIVEN* the overview lists a live session
- *WHEN* the human selects the row
- *THEN* that session's buffer is displayed

** Quit a session
- *GIVEN* the overview lists a live session
- *WHEN* the human quits the row
- *THEN* that session is asked to shut down immediately, without a confirmation prompt, and the row reflects the result

** Quitting a mid-turn session is not confirmed
- *GIVEN* the overview lists a session whose model is mid-turn
- *WHEN* the human quits the row
- *THEN* the session is shut down without asking for confirmation first

** Interrupt a turn
- *GIVEN* the overview lists a session that is mid-turn
- *WHEN* the human interrupts the row
- *THEN* that session's turn is interrupted

** Acting on a dead session
- *GIVEN* a row's session has exited
- *WHEN* the human tries to interrupt it
- *THEN* the overview reports that there is nothing to interrupt rather than signalling an unhandled error
* One permission UI serves every backend
The permission menu SHALL live on ~agent-backend~ so that a backend with
its own permission gate answers through the same buffer as the Claude hook,
rather than each backend growing its own surface.
** Opencode's gate uses the shared menu
- GIVEN an opencode session that asks for a permission decision
- WHEN the decision is raised
- THEN it appears in the same menu buffer, and answering it replies to
  opencode
* Start another, parallel agent conversation
The agent-backend module SHALL provide a command ~agent-backend-start-another~
that starts a fresh conversation with the preferred backend
(according to ~agent-backend-preference~), resolving the backend exactly as
~agent-backend-start~ does, and SHALL never reuse or reset the conversation
buffer it is invoked from — a running conversation is joined, not restarted.
** Opens a fresh conversation under opencode
- WHEN the preferred backend is opencode and ~agent-backend-start-another~ is invoked
- THEN a new session is created via ~opencode-client-create-session~
** Opens a fresh conversation under Claude
- WHEN the preferred backend is Claude and ~agent-backend-start-another~ is invoked from inside a Claude conversation buffer
- THEN a new conversation buffer is created (not the current one restarted) and its first prompt is composed
** Exposed in the conversation and overview keymaps
- WHEN a ~claude-client-mode~ or ~agent-session-overview-mode~ buffer is focused
- THEN ~agent-backend-start-another~ is bound in that mode's keymap
* Standing turn-state indicator on a conversation buffer
The agent-backend module SHALL expose a conversation's turn state through a
generic ~agent-backend-turn-state~ returning one of ~working~, ~idle~, or
~finished~, and its current-turn elapsed time through ~agent-backend-turn-elapsed~
(seconds, or nil when no turn is working). The default MUST NOT over-claim: a
backend that tracks no turn state reads ~finished~ and elapsed nil.
** Reports a mid-turn conversation as working
- WHEN ~agent-backend-turn-state~ is called on a conversation whose model is working on a turn \\
  THEN it returns ~working~
** Reports a live-but-idle conversation as idle
- WHEN ~agent-backend-turn-state~ is called on a conversation whose process is alive but no turn is in flight \\
  THEN it returns ~idle~
** Reports a settled conversation as finished
- WHEN ~agent-backend-turn-state~ is called on a conversation whose process has exited or which never started \\
  THEN it returns ~finished~
** Elapsed time tracks only a working turn
- WHEN ~agent-backend-turn-elapsed~ is called on a working conversation \\
  THEN it returns the seconds since that turn started; when no turn is working it returns nil
* The conversation mode line shows the state
Every ~agent-backend-mode~ conversation buffer SHALL carry a standing
mode-line indicator of its turn state, updated from the transitions that change
the state, and SHALL show the elapsed time while working.
** Mode line reflects the turn state
- WHEN a conversation buffer derived from ~agent-backend-mode~ is displayed and its turn state changes \\
  THEN its mode line shows the new state (working / idle / finished)
** Mode line shows elapsed time while working
- WHEN a ~working~ conversation's mode line is rendered \\
  THEN it includes the seconds the current turn has been running
* A session scope answers every gated call without asking, until turned off
The permission menu SHALL offer a session-scoped option, alongside allow-once
and the durable always-allow rule, that answers the current decision `allow`
and records a per-Emacs-session flag so every later gated call is answered
`allow` without raising a decision buffer.
- The flag SHALL live in memory only.
- The flag MUST NOT be written to any settings file, so a new session starts gated again.
It SHALL be possible to turn the session scope off mid-session.
The active session scope SHALL be visible.
The session scope MUST NOT loosen tools that are structurally closed
(`apply_diff`, `--disallowedTools`): it waives the asking, never the closure.
The session scope SHALL apply to every backend that asks through the shared
`agent-permission-request` entry point -- the Claude hook, the opencode
permission stream, and the manual escape hatch alike.
** The menu offers a session-scope key
- GIVEN a pending permission decision in an `agent-permission` buffer
  WHEN the session-scope key (`z`) is pressed
  THEN the current decision is answered `allow` and the session flag is set
  AND no settings file is written
** A gated call while the session scope is on resolves without a buffer
- GIVEN the session-scope flag is set
  WHEN `agent-permission-request` is called for a gated tool
  THEN the decision is answered `allow` immediately
  AND no decision buffer is created and nothing enters the pending registry
** The session scope can be turned off mid-session
- GIVEN the session-scope flag is set
  WHEN `agent-permission-session-allow-all-mode` is invoked with argument 0
  THEN the flag clears and a later gated call raises a real decision buffer again
** The active session scope is visible
- WHEN the session-scope flag is set
  THEN a mode-line lighter indicating it is active appears in buffers
** The closure of structurally-closed tools is unchanged
- WHEN the session-scope flag is set
  THEN a tool that is structurally closed (`apply_diff`, a `--disallowedTools`
    entry) is still not callable; only the asking about it is waived
** Every backend answers through the same session scope
- GIVEN the session-scope flag is set
  WHEN a permission request arrives from any backend that uses the shared menu
  (Claude hook, opencode stream, manual escape hatch)
  THEN it is answered `allow` without a buffer, by the same code path
* Background-agent lifecycle is part of the shared vocabulary
The =agent-backend-event-functions= ~:kind~ vocabulary SHALL cover background-agent
lifecycle with at least ~agent-started~, ~agent-update~, ~agent-finished~, and
~agent-killed~. ~agent-started~ SHALL carry an ~:agent~ identity, the ~:name~
of the tool that spawned the agent, and the ~:task~ the agent was asked to do;
~agent-update~ SHALL carry ~:agent~ and ~:text~; ~agent-finished~ SHALL carry
~:agent~, a ~:status~ of ~done~ or ~failed~, and ~:result~ text. A backend that
cannot attribute an event SHALL omit the key rather than invent it, and
subscribers SHALL ignore unknown kinds (existing rule).
** A fanned-out agent appears as agent-started
- WHEN a conversation's turn fans out to a background agent via a spawn tool
- THEN the seam publishes ~agent-started~ with the agent's identity, the spawn
  tool name, and the task it was asked to do
** An agent's output flows as agent-update
- WHEN a running background agent produces output attributable to it
- THEN the seam publishes ~agent-update~ carrying the text
** A completing agent leaves running via agent-finished
- WHEN a background agent's result arrives
- THEN the seam publishes ~agent-finished~ with ~:status~ ~done~ (or ~failed~
  on error) and the result text
* A conversation tracks the agents it spawned
The agent-backend module SHALL maintain a per-conversation (buffer-local)
registry of the background agents that conversation spawned, recording each
agent's identity, spawn tool, task, status (running / done / failed), its
isolated-output buffer, and start/finish markers. The registry SHALL be
buffer-local with no global session store, and SHALL be derived from the ~tool-use~
and ~tool-result~ (or backend completion) events already on the seam — a spawn
tool (~:name~ in =agent-backend-spawn-tool-names=) opens an agent, its result
closes it.
** A spawn tool opens a running agent
- WHEN the conversation publishes a ~tool-use~ whose ~:name~ is in =agent-backend-spawn-tool-names=
- THEN its registry holds a ~running~ entry whose task is that tool's input
** A result closes the agent it opened
- WHEN a ~running~ agent's matching ~tool-result~ (or backend completion) arrives
- THEN the entry becomes ~done~ (or ~failed~ on error) and records the result
** Every conversation keeps its own agents
- WHEN two conversations each spawn agents
- THEN each holds only its own, because the registry is buffer-local
* Spawned agents are visible and actionable
Emacs SHALL provide a command listing the background agents a conversation
spawned — identity, status, and task — and SHALL let the human open one
agent's output in its own buffer and ask to stop one. Opening an agent SHALL
show the task and the agent's accumulated output in an isolated buffer.
Stopping one SHALL raise the intent to the backend via =agent-backend-kill-agent=,
and a backend with no way to stop a single background agent SHALL say so
rather than silently doing nothing. When a spawned agent reaches ~done~ or
~failed~, the list SHALL reflect it without a manual refresh.
** The list shows identity, status, and task
- WHEN the list for a conversation with spawned agents is opened
- THEN each agent appears as a row with its identity, status, and task
** An agent's output opens on its own
- WHEN the human opens a listed agent
- THEN an isolated buffer shows the task it was asked to do and its output
** Stopping is honest about what a backend can do
- WHEN the human asks to stop an agent on a backend that cannot stop a single
  background agent
- THEN the command reports that the backend cannot rather than pretending
** A finish is noticed without a refresh
- WHEN the list is on screen and a running agent reaches ~done~ or ~failed~
- THEN its row updates by itself
